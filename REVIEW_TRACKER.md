## Status and update rules

- **Open**: the issue remains and its fix is not complete.
- **Partial**: some entrypoints or subitems are fixed; specify what remains.
- **Changed; verification pending**: code changed, but required validation remains.
- **Complete**: changes and required checks are complete within the stated scope; record validation limits.
- **Verification pending**: a compatibility or timing risk requiring checks, not a reproduced failure.
- **No change needed**: current behavior satisfies the data stage's contract; retain the rationale.

P1 concerns data correctness, operation, or effective configuration. P2 primarily concerns readability, defaults, paths, and documentation consistency.

After each change, in the same turn:

1. Update the issue's status, completed work, remaining work, verification, and last-updated date.
2. Append the date, ID, actual files, changes, and verification to the history; do not overwrite historical records.
3. Do not mark untouched entrypoints complete or report unrun tests as passing.
4. Assign new IDs to new issues; do not renumber or reuse existing IDs. Record independent changes outside the original scope as well.
5. Base status on actual working-tree code, not whether Git shows M or a commit exists.
